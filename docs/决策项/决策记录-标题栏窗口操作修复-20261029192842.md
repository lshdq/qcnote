## 决策列表

### DEC-001: 根因修复方式采用 ListView 条件 interactive（事件穿透）
- 阶段：阶段 2 方案设计
- 背景：`TitleBar.dragArea` 在最底层，几乎被 `DocumentTabs` 的 `ListView`（默认 `interactive: true`，接受边界内全部左键按下，含空白区）整体遮蔽，需让空白区按压事件到达 `dragArea`
- 可选方案：
  - A. `ListView` 设 `interactive: contentWidth > width`，仅溢出时启用 Flickable 交互；未溢出时空白区按下事件向下传播给 `dragArea`
  - B. 在 `DocumentTabs` 内 ListView 上/下叠加一层空白区 MouseArea
  - C. 把 `TitleBar.dragArea` 提到 `documentTabs` 之上（提高 z）
- 最终选择：A
- 选择理由：B 无论在上层（挡住 Tab 点击）还是下层（仍被 interactive 的 ListView 吞掉）都不可行；C 挡住整个 Tab 区，破坏 Tab 交互；A 改动最小（一行绑定），仅在"无需滚动"时精确关闭事件吞掉，保留 Tab 全部既有行为与溢出滚动
- 影响：Tab 溢出撑满标题栏时无空白可拖拽窗口（此时本无空白区，与 Chrome 等一致，属正常边界）

### DEC-002: 最大化拖拽还原时按光标比例重新定位窗口
- 阶段：阶段 2 方案设计
- 背景：最大化时拖拽需还原窗口并继续系统拖拽；直接 `showNormal()` + `startSystemMove()` 会先跳回上次最大化前的几何位置，产生明显跳变
- 可选方案：
  - A. 直接 `showNormal()` + `startSystemMove()`，接受跳变
  - B. 用 `mapToGlobal()` 取光标全局位置，`showNormal()` 后将窗口定位到光标下方（顶边对齐、水平锚点按按下点比例），再 `startSystemMove()`
- 最终选择：B
- 选择理由：对齐 Windows 原生体验（还原后光标仍停留在标题栏上）；`Item.mapToGlobal()` 自 Qt 6.8 可用（项目 Qt 6.11.2），仅增加几行代码
- 影响：还原时程序化设置一次窗口 x/y，随后交由系统拖拽循环接管

### DEC-003: 附着 ScrollBar 与 ListView 条件 interactive 联动（审查 #1/#2 修复）
- 阶段：阶段 7 代码审查修复
- 背景：审查 offscreen 实测发现，Material 风格下 attached `ScrollBar.horizontal`（`policy: AsNeeded`）未溢出时 visible 恒真（仅 contentItem opacity 隐藏，opacity 不影响鼠标命中），几何为 Tab 条底部全宽 16px 条带，`handlePress` 无条件接受左键——Tab 条下半空白区拖拽/双击失效（需求 1/2 区域性缺失），且 Tab delegate/关闭按钮下半部点击被吞（基线即存在的死区）。DEC-001 只解除了 Flickable 的吞事件，未解除同层级 ScrollBar 的
- 可选方案：
  - A. ScrollBar 同样设 `interactive: contentWidth > width`（非 interactive 时 C++ 侧 `setAcceptedMouseButtons(Qt::NoButton)` 完全退出命中；溢出时保持可拖动）
  - B. 未溢出时 `policy: AlwaysOff`（visible=false 不参与命中）
- 最终选择：A
- 选择理由：与 ListView 条件一致（同一绑定两处复用，语义统一）；不改变滚动条视觉行为（未溢出时本就无 active 显示）
- 影响：一行绑定；同时消除 #1（空白区下半失效）与 #2（Tab 下半点击死区，pre-existing）

### DEC-005: 采纳第 2 轮复审可选项（条件表达式去重 + 文档统计修正）
