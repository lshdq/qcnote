## 决策列表

### DEC-001: 文档落盘位置沿用项目 docs/ 目录
- 阶段：阶段 3（生成文档）
- 背景：dev-workflow 默认在项目根 `.localdoc/` 下生成需求文档与测试用例；但本项目既有 15 个需求文档、16 个决策记录均落盘于 `docs/` 下同名子目录（项目 AGENTS.md 亦如此声明目录职责）
- 可选方案：`.localdoc/`（skill 默认）；`docs/`（项目既有惯例）
- 最终选择：`docs/需求文档`、`docs/测试用例`、`docs/决策项`、`docs/审查记录`
- 选择理由：项目级规范更具体时以项目规范为准；保持仓库文档体例与历史一致，便于检索
- 影响：无功能影响；审查记录同样落 docs/审查记录

### DEC-002: 缓存条目主键用文档 uid（构造时生成 UUID）而非 URL
- 阶段：阶段 2（方案设计，获批方案组成部分）
- 背景：未命名文档无 URL；另存为后 URL 变化；按 URL 做主键需处理键迁移且无法覆盖未命名文档
- 可选方案：URL 哈希做文件名 + 未命名单独编号；文档不可变 uid 做主键
- 最终选择：`Document` 构造时生成不可变 `uid()`（QUuid），缓存文件名 `<uid>.json`，条目内记录当前 url
- 选择理由：主键稳定、生命周期与文档一致，另存为仅更新条目内 url 字段；恢复时按条目 url 匹配目标文档
- 影响：`Document` 新增只读接口；恢复应用后旧条目删除、后续编辑按新文档 uid 重新落盘

### DEC-003: 缓存清理统一绑定"modified 变 false"+"关闭时仍 modified"
- 阶段：阶段 2（方案设计，获批方案组成部分）
- 背景：用户确认"保存成功清理、放弃关闭清理"；而"内容回到基线"存在多条路径（保存、另存为、撤回到原内容、按编码重载覆盖）
- 可选方案：仅在 DocumentManager 保存/关闭代码路径上逐一挂钩；统一按 Document 信号语义清理（modifiedChanged→false 删条目；documentClosed 且仍 modified 删条目）
- 最终选择：信号语义统一清理
- 选择理由：零侵入 DocumentManager 既有保存/关闭代码，天然覆盖全部置干净路径，不会因新增路径遗漏；撤回到基线时缓存内容与磁盘一致，删除无信息损失
- 影响：DocumentManager 无需为缓存改动保存/关闭逻辑

### DEC-004: 缓存目录定位复用便携检测
- 阶段：阶段 2（方案设计，获批方案组成部分）
- 背景：需要与 qcnote.ini 一致的便携/安装模式目录语义
- 可选方案：独立实现目录探测；复用 `SessionManager::resolvePortableIniPath` 判定便携后取 exe 目录
- 最终选择：便携标记存在 → `<exe目录>/drafts/`；否则 `QStandardPaths::AppLocalDataLocation` + `/drafts/`
- 选择理由：与既有便携语义单一事实源，行为一致；AppLocalDataLocation 由组织名/应用名（qcnote）派生
- 影响：便携模式切换（移动 exe/增删标记）后旧缓存失联不恢复，已作为边界约束记录

### DEC-005: 防抖间隔 1000ms
- 阶段：阶段 2（方案设计，获批方案组成部分）
- 背景：内容级写盘比会话元数据（500ms）更重，需平衡丢失窗口与 IO 压力
- 可选方案：500ms（同会话）；1000ms；2000ms
- 最终选择：1000ms 单触发 CoarseTimer（restart 语义聚合高频编辑）
- 选择理由：崩溃丢失窗口约 1 秒（用户可接受），MB 级文本重写频率降低一半以上
- 影响：需求文档"崩溃最多丢最后约 1 秒修改"表述与此一致

### DEC-006: 冲突对话框采用单一汇总列表
- 阶段：阶段 2（方案设计，获批方案组成部分）
- 背景：多个条目同时冲突（外部修改/文件缺失）时逐文件弹窗体验差
- 可选方案：逐文件弹窗；单对话框列出全部冲突，「恢复」「丢弃」按钮统一应用
- 最终选择：单对话框汇总（列出冲突文件），「恢复」全量应用、「丢弃」全量丢弃
- 选择理由：实现简单、操作少；编辑器场景同时多冲突罕见，不牺牲关键交互
- 影响：不提供逐条差异化选择（如记录为后续增强项）

### DEC-007: 恢复应用后删除旧条目文件
- 阶段：阶段 2（方案设计，获批方案组成部分）
- 背景：恢复目标文档是新建/既有文档，uid 与条目 uid 不同（未命名重建必为新文档）
- 可选方案：保留条目复用旧 uid；应用后删除条目、后续编辑按新 uid 重写
- 最终选择：应用（含丢弃）后即删除条目文件
- 选择理由：避免 uid 漂移带来的匹配歧义；同时天然承担孤儿/损坏条目清理职责，目录不留陈旧数据
- 影响：恢复后到下一次防抖落盘之间（约 1 秒内）的二次崩溃可能丢刚恢复的草稿，概率极低，接受

### DEC-008: 不新增设置项，缓存明文 JSON 存储
- 阶段：阶段 2（方案设计，获批方案组成部分）
- 背景：是否提供"启用/停用草稿缓存"开关；缓存是否加密
- 可选方案：新增设置项；默认开启无开关。明文/加密
- 最终选择：默认开启无开关；明文 JSON
- 选择理由：对齐会话恢复"不新增设置项"的既有决策；缓存与被编辑文件同信任级（磁盘上的原文件本身即明文），加密无实质安全收益
- 影响：文档以边界约束形式明示

### DEC-009: 同 URL 多条目按 savedAt 最新去重（审查应改 #1 修复）
- 阶段：阶段 7 修复轮
- 背景：冲突框 Esc（未决保留条目）+ 再次崩溃可产生同 URL 双条目；目录序处理会让较旧草稿覆盖较新草稿，静默丢一份草稿
- 可选方案：resolveConflicts 应用前排序取最新；restoreDrafts 解析后分类前按 URL 去重（保留 savedAt 最新，落选立即删文件）
- 最终选择：解析后分类前统一去重；仅 url 非空条目参与，savedAt 缺失按 0（最旧），平局按 uid 字典序保留较大者（确定性，不依赖目录枚举序）
- 选择理由：静默路径与冲突路径共用同一去重结果，conflictsFound 对同一 url 至多一项；落选条目立即删除避免陈旧数据再参与后续会话
- 影响：极端双崩溃场景下旧草稿被明确丢弃（仅保最新），有 3 个专项单测锁定

### DEC-010: QML 测试草稿目录隔离采用预清理+结束清理（审查应改 #2 修复）
- 阶段：阶段 7 修复轮
- 背景：7 个实例化 Main.qml 的测试 exe 的草稿目录位于 %LOCALAPPDATA%\<测试名>\drafts，跨运行持久；脏文档残留 + 防抖写盘会造成下轮测试恢复出额外文档（计数断言偶发失败）并污染用户目录
- 可选方案：QStandardPaths::setTestModeEnabled；每次运行改唯一应用名；main() 中引擎加载前 removeRecursively 预清理 + 返回前结束清理
- 最终选择：预清理 + 结束清理（不用 setTestModeEnabled、不改应用名）
- 选择理由：与生产默认目录解析精确一致、零全局路径模式副作用、不产生目录漂移与积累；预清理隔离跨轮残留，结束清理防用户目录污染；实证实验（预置伪造残留 → 测试通过 → 目录被清）验证有效
- 影响：仅测试 main() 变更（7 处），生产代码零改动；进程被强杀时残留仍可能，由下轮预清理兜底

### DEC-011: 审查可选项 #3/#5 记录为后续迭代，不在本轮处理

- 背景：#3 代开路径固定自动识别编码，原会话为强制编码且会话记录缺失时 baselineHash 可能误判（多弹一次冲突框，结果仍正确）；#5 代开 isFile 检查与读取间 TOCTOU 双弹窗（均无害）
- 可选方案：#3 代开改走条目 encoding 强制解码；维持现状
- 最终选择：维持现状，记录后续迭代
- 选择理由：#3 两个方向的边界会互相转化（强制按条目编码在"用户已切编码未保存"场景反而制造冲突），收益不明确；#5 审查者本身建议接受（消除需 DocumentManager 提供静默打开入口，改动面大）
- 影响：低频冗余提示，无数据正确性影响
