## 决策列表

### DEC-001: GBK 编解码采用 GB18030 转换器
- 阶段：方案设计（阶段 2，已批准方案补录）
- 背景：需支持 GBK，Qt 6 的 QStringConverter 内置 GB18030（GBK/GB2312 超集）而非独立 GBK 条目。
- 可选方案：① QStringConverter::GB18030；② 自研 GBK 码表；③ 引入 ICU/iconv 等第三方依赖。
- 最终选择：① GB18030。
- 选择理由：Qt 6.2+ 内置 CJK 码表无第三方依赖，完全兼容 GBK/GB2312 文件，往返安全；自研与第三方成本/风险高。
- 影响：界面统一显示 "GBK"；识别到的"GBK"实际按 GB18030 解码（覆盖面更广）。

### DEC-002: 自动识别策略为 BOM → 严格 UTF-8 校验 → GBK
- 阶段：方案设计（阶段 2，已批准方案补录）
- 背景：GBK 字节序列几乎总能被 GB18030 解码，无法靠"解码成功"区分；UTF-8 多字节结构严格，可做合法性校验。
- 可选方案：① BOM → 严格 UTF-8 校验 → GBK；② 统计启发式（字符频率/双字节分布打分）；③ 始终按系统 locale。
- 最终选择：①。
- 选择理由：确定性强、O(n) 单遍、纯 ASCII 与常规中文场景准确；启发式复杂且不稳定；系统 locale 依赖运行环境不可移植。极端误判（GBK 字节恰为合法 UTF-8）由手动重新加载兜底。
- 影响：纯 ASCII 判为 UTF-8；误判场景需用户一次手动纠正。

### DEC-003: 编码识别逻辑放在存储层（独立 EncodingDetector），DocumentManager 仅传编码意图
- 阶段：方案设计（阶段 2，已批准方案补录）
- 背景：识别需要原始字节，只有存储层拿得到；将来网络存储可复用。
- 可选方案：① 存储层内嵌识别器并独立成类；② DocumentManager 读字节后识别再传给存储层（需读两次文件或泄漏字节抽象）。
- 最终选择：①。
- 选择理由：保持 DocumentStorage 字节→文本职责边界，识别器可独立单测，未来存储扩展零成本复用。
- 影响：LocalStorage::read 保留无编码重载（自动识别）+ 增加强制编码重载。

### DEC-004: 编码元数据挂 Document 属性（与 lineEnding 同构）
- 阶段：方案设计（阶段 2，已批准方案补录）
- 背景：编码需跨打开/保存/会话跟随文档。
- 可选方案：① Document 新增 encoding/hasBom 属性；② DocumentManager 维护 url→编码映射表。
- 最终选择：①。
- 选择理由：与既有 lineEnding 模式一致，QML 可直接绑定，生命周期天然跟随文档，无映射表同步问题。
- 影响：applyLoadedState 签名扩展（内部 API，调用点少，同步更新）。

### DEC-005: 「通过编码保存」设计为一步完成（设编码 + 立即保存）
- 阶段：方案设计（阶段 2，已批准方案补录）
- 背景：用户已选"转换保存"语义；若仅设标记不保存，用户容易误解转换已完成。
- 可选方案：① saveWithEncoding = 设置编码 + 立即保存；② 仅 setSaveEncoding 置标记，等用户再 Ctrl+S。
- 最终选择：①。
- 选择理由：一步到位符合"转换"预期，避免半完成状态；未命名文档返回 false 由 UI 转另存为（另存为按已设编码写出）。
- 影响：菜单触发即落盘；GBK 不可编码时整体失败、编码标记不产生误导（错误提示指引）。

### DEC-006: GBK 可编码性校验在写盘前完成，失败阻止保存
- 阶段：需求澄清（用户决策）+ 方案设计细化
- 背景：用户已选"保存失败并提示"。
- 可选方案：① 写盘前逐段校验，失败报错含字符与行号；② 直接编码靠 Qt 替换字符 '?'。
- 最终选择：①。
- 选择理由：防止数据静默损坏；错误定位降低用户修复成本。
- 影响：saveWithEncoding/write 对不可编码内容返回 false 并给出定位消息。

### DEC-008: 重新加载的未保存修改确认由 QML 层负责，C++ 不拦截
- 阶段：方案设计（阶段 2，已批准方案补录）
- 背景：reloadWithEncoding 会以磁盘内容覆盖内存修改。
- 可选方案：① QML 弹确认框后调用（与关闭标签页未保存确认同模式）；② C++ 内弹框/拒绝。
- 最终选择：①。
- 选择理由：与既有 unsavedDialog 交互模式一致，UI 决策留在 UI 层，C++ 保持纯接口。
- 影响：QML 需新增确认框；C++ 侧 reload 直接执行。

### DEC-009: GBK 编解码后端改用 Win32 NLS API（CP936），取代 QStringConverter::GB18030
- 阶段：执行开发（阶段 5，T2 第 0 步验证触发）
- 背景：开发子智能体实证本机官方 Qt 6.11.2（MinGW 与 MSVC kit 均同）未编译 `big_codecs` 特性：`QStringConverter::GB18030` 编译期不存在、`encodingForName("GB18030")` 运行时找不到、Qt5Compat 未安装（且其 CJK 编解码同样受 big_codecs 特性控制）。DEC-001 的前提「Qt 6.2+ 内置 CJK 码表」仅对自行开启 `-feature-big_codecs` 的 Qt 构建成立，官方二进制包不成立。
- 可选方案：① Win32 NLS API（CP936，MultiByteToWideChar/WideCharToMultiByte）；② 自编译 Qt 开启 big_codecs；③ 安装 Qt5Compat QTextCodec；④ 引入 ICU/iconv 第三方库；⑤ QStringConverter::System 系统 locale；⑥ 自研 GBK 码表。
- 最终选择：① Win32 NLS API（CP936）。
- 选择理由：零新增依赖（NLS 为 Windows 内置，代码页 936 在任意 locale 的 Windows 上可用，不依赖系统语言设置）；不改变官方 Qt 工具链与构建环境；CP936 即 GBK 的 Windows 官方实现，正是需求范围（GB18030 特有 4 字节扩展超出 GBK 需求）；QString 内部即 UTF-16，与 WideChar 系 API 天然匹配；项目本就 Windows 平台优先（Q_OS_WIN + 注册表集成），编解码封装在单一组件（src/platform/gbkcodec），未来跨平台时只替换该组件。②需自维护 Qt 构建数小时且长期偏离官方包；③模块未安装且大概率同样被裁剪、属弃用兼容层；④便携版打包体积与依赖管理代价高；⑤非中文 Windows 不可用；⑥两万余字码表维护风险高。
- 影响：识别/转换/保存/会话等全部设计（DEC-002~DEC-008）不变，仅编解码实现层替换；GBK 解码由 GB18030 改为 CP936（GBK 文件行为一致，GB18030 4 字节扩展字符以 U+FFFD 呈现，超需求范围）；不可编码检测用 WideCharToMultiByte 默认字符替换标志实现。需求文档「依赖」节与相关 GB18030 表述同步修订。
