## 决策列表

### DEC-001: 技术路线——TextArea 上自建多层实现，不引入第三方编辑器组件
- 阶段：方案设计（阶段 2）
- 背景：Qt Quick TextEdit 原生不支持多光标/列选区，需要选择实现路线
- 可选方案：1) 保留 TextArea，叠加自建多光标层；2) 换用 QScintilla/QTextEdit 小部件组件；3) 完全自绘编辑器
- 最终选择：方案 1
- 选择理由：保持 Qt Quick 技术栈一致性（项目约定 QML 优先）；TextArea 已承担渲染/滚动/IME/撤销基础；方案 2 引入 Widgets 混合与依赖冲突风险；方案 3 工作量与风险远超收益
- 影响：多光标能力受 TextArea 事件/坐标机制约束（覆盖层跟随、事件拦截为主要技术风险点）

### DEC-002: 架构分层——纯逻辑引擎与 GUI 分离
- 阶段：方案设计（阶段 2）
- 背景：多光标算法（列选区、Ctrl+D、批量编辑偏移计算）边界多，需可自动化验证
- 可选方案：1) C++ 纯逻辑引擎（仅 QtCore）+ C++ 控制器 + QML 覆盖层；2) 全 QML/JS 实现；3) 全部逻辑放控制器
- 最终选择：方案 1
- 选择理由：引擎只吃 QString、输出编辑指令与光标列表，可在控制台 QtTest 全量单测；QML/JS 实现难以单测且算法复杂易错；控制器承上启下保持 QML API 精简
- 影响：新增 `src/editor/` 目录两个 C++ 类；编辑指令从后往前应用成为引擎与控制器间的稳定契约

### DEC-003: 撤销原子性——单批编辑合并为一次撤销
- 阶段：方案设计（阶段 2）
- 背景：一次按键在 N 个光标产生 N 处编辑，逐处撤销体验破碎
- 可选方案：1) QTextCursor::beginEditBlock/endEditBlock 包裹整批；2) 每处编辑独立撤销步骤
- 最终选择：方案 1
- 选择理由：与用户已确认需求（一次按键单次撤销）一致，且复用 QTextDocument 原生撤销栈，与 TextArea 原生 Ctrl+Z 无缝兼容
- 影响：控制器所有编辑必须经统一入口应用；引擎输出纯指令、不触碰文档

### DEC-004: 单光标零接管
- 阶段：方案设计（阶段 2）
- 背景：事件拦截层若全程接管按键，回归风险大
- 可选方案：1) 仅在多光标激活或命中多光标触发键时拦截，单光标普通编辑完全走原生路径；2) 全程接管所有编辑键
- 最终选择：方案 1
- 选择理由：现有单光标行为零变化（回归风险最小），拦截面小、易验证
- 影响：多光标激活时收到未支持命令需先退单光标再转原生处理（已纳入需求边界）

### DEC-005: 中文输入法——提交分发、预编辑保持原生
- 阶段：方案设计（阶段 2）
- 背景：QML TextArea 的 IME 预编辑由原生渲染于主光标，多光标下需定义 IME 行为
- 可选方案：1) C++ 事件过滤器拦截 QInputMethodEvent，把 commit 字符串分发到所有光标，预编辑保持原生主光标显示；2) 多光标激活时禁用 IME；3) 自绘多光标预编辑
- 最终选择：方案 1
- 选择理由：与 VS Code 行为一致（用户已确认的体验基准）；方案 2 中文用户不可接受；方案 3 复杂度高收益低
- 影响：控制器需以事件过滤器方式挂接 TextArea item

### DEC-006: 粘贴分发策略——行数匹配逐行分发，不匹配整份插入
- 阶段：方案设计（阶段 2）
- 背景：多光标粘贴多行剪贴板存在分发歧义
- 可选方案：1) 剪贴板行数等于光标数时逐行分发，否则每光标插入整份文本（VS Code 语义）；2) 永远整份插入；3) 永远按行截断分发
- 最终选择：方案 1
- 选择理由：列复制（按行拼接）后原位列粘贴的往返体验正确；不匹配时语义安全不丢内容；用户已确认
- 影响：无额外状态，纯规则判定

### DEC-007: 交互用例测试策略——新增持久化 offscreen 集成测试目标
- 阶段：独立测试（阶段 6）
- 背景：TC-101 至 TC-113 交互用例默认只能人工验证，无 GUI 自动化路径
- 可选方案：1) 新增 test_editor 可执行目标，真实组件接线 + offscreen 合成键鼠/输入法事件持久化自动化；2) 仅留人工待验清单
- 最终选择：方案 1
- 选择理由：列式编辑为编辑器核心交互，回归风险高；T3 阶段已实证 offscreen 合成事件可行；持久化测试成为后续迭代的回归资产
- 影响：测试范围扩大（+15 用例），构建时间小幅增加；真实 IME 视觉/DPI/闪烁观感仍留人工

### DEC-008: setPosition 越界告警根治方案——控制器编辑事务状态前置 + contentsChange 钳制
- 阶段：缺陷修复（阶段 6）
- 背景：多光标批量编辑期间 QML 绑定重算经 positionToRectangle（Qt 内部无钳制 setPosition）读到引擎旧位置，文档缩短时产生 13 条越界告警；初版修复（endEditBlock 前钳制）仅覆盖部分路径
- 可选方案：1) applyBatch 引擎状态更新前置到文档编辑之前 + contentsChange 非批量变化时静默钳制；2) 仅 QML 侧延迟同步；3) 接受 Qt 内部噪声
- 最终选择：方案 1
- 选择理由：从时序上保证编辑事务期间任何 QML 中间重算读到合法位置；对外信号语义不变；告警归零且 86 用例无回归
- 影响：控制器内部中间态顺序固定（引擎状态先于文档编辑），后续维护需保持该次序

### DEC-009: 一轮审查的可选项全量处理
- 阶段：审查修复（阶段 7）
- 背景：一轮审查 0 阻塞 / 1 应改 / 6 可选，可选项可随本次处理或留后续迭代
- 可选方案：1) 仅修应改项；2) 应改 + 可选全部修复
- 最终选择：方案 2
- 选择理由：6 个可选项均为小而明确（状态机一致性、状态栏信息完整、修饰键防御、列选残留、Ctrl+D 回退、文档注明），一次收敛避免技术债；复测成本可控
- 影响：修复轮次增加一轮，最终 0/0/0 收敛

### DEC-010: Ctrl+D 相交跳过语义——严格重叠（端点相接允许追加）
- 阶段：审查修复（阶段 7，二轮复审 P-1）
- 背景：一轮修复把"完全重合才跳过"扩为闭区间相交（端点相接也跳过），导致 foofoo 连续重复词 Ctrl+D 无响应且被测试断言固化；与需求文档功能表（VS Code 基准）冲突
- 可选方案：1) 严格重叠判定（start < e && s < start + length），端点相接允许追加；2) 维持闭区间跳过
- 最终选择：方案 1
- 选择理由：需求文档为用户确认的功能基准且明示 VS Code 风格（相邻匹配可追加）；assembleBatch 重叠过滤本就用严格比较，相邻编辑不会被丢弃；部分重叠核心场景（aaaa 选 [1,3)）两种判定结论一致
- 影响：tc023/tc013 断言与 TC-023 文档同步修订；连续重复词场景行为与 VS Code 对齐

### DEC-011: 列选拖拽鼠标抓取保持——preventStealing + 接受纯修饰键
- 阶段：用户验收缺陷修复（交付后）
- 背景：真机 Alt+Shift+鼠标拖拽列选区"完全没反应"（offscreen 合成测试无法复现）。两轮带日志诊断（真机启动 + stderr 捕获 + 用户复现）：第一轮日志显示拦截链路正常但拖拽约 500ms/12px 后 MouseArea 收到 onCanceled（鼠标抓取被夺走）；第一轮修复（接受纯修饰键阻断 Alt 自动重复经 DefWindowProc 触发 WM_CANCELMODE）单独无效；第二轮加入 preventStealing 后真机验证通过（拖拽 37/191+ 次移动全程正常、release 正常完成、4 光标 2 选区）
- 最终根因：ScrollView 内部 Flickable 在拖拽超过阈值（约 10px，与第一轮日志 cancel 时点吻合）后经子事件过滤器（childMouseEventFilter）抢夺子项鼠标抓取；原生 TextArea 选择内部自带保持抓取（keepMouseGrab）故从未受影响，覆盖层 MouseArea 未设 preventStealing 而被抢
- 可选方案：1) MouseArea 设 preventStealing: true + 接受纯修饰键（防御性保留）；2) 仅修饰键接受（第一轮方案，实证不充分）；3) onCanceled 后重新抓取（治标，系统态下不可靠）；4) PointerHandler 重写交互层（风险大）
- 最终选择：方案 1
- 选择理由：直击根因且最小改动；修饰键接受虽非本缺陷根因，但属正确防御（阻止未处理系统键到达 DefWindowProc）；86 项自动化测试无回归
- 影响：`src/qml/EditorArea.qml` MouseArea 增加 preventStealing: true（含根因注释）、Keys.onPressed/onReleased 对纯修饰键 event.accepted = true；新增 TC-115 真机人工验证项；测试盲区记录——QQuickFlickable 抢夺路径在 offscreen 合成事件下不触发，此类缺陷只能真机验证
