- Win32 NLS 边界探针实证（源码与产物保留于 `D:\temp\aiRunner\opencode\qcnote-review-gbk-probe\`）：
  1. ASCII `?` 在 CP936 直接映射、`usedDefaultChar=FALSE`——**排除**"含问号文本被误阻止保存 GBK"的风险；
  2. U+FFFD 在 CP936 无映射（含坏字节的 GBK 文档直接 Ctrl+S 会按需求失败并定位提示，符合 DEC-006，不静默替换）；

  6. 孤立代理项被 `WideCharToMultiByte` 正确拒绝；代理对作为整体探测不可编码（emoji 定位路径正确）。
- 框架语义查证（Qt 源码 `qquickmenu.cpp`）：菜单项点击时框架内部槽 `onItemTriggered` 先 `dismiss()` 同步关闭菜单层级，再执行 QML `onTriggered`——真实菜单路径下 `uiLocked()` 的 `titleBar.menuVisible` 已为 false，编码菜单操作不会被误拦截（与既有"保存/另存为"菜单项同模式，既有功能佐证）。

## 4. 其他发现（复核成立，按严重度排序）

**阻塞：无。应改：无。**

以下为可选项与实证记录（均不阻塞合并）：

1. **[可选] QML 悬垂防御** `src/qml/Main.qml:615-619` — `onAccepted` 中 `doc && doc.url.toString()`：若 `reloadConfirmDoc` 指向的 Document 在确认框展示期间被析构（程序化路径），`doc.url` 为 undefined、`.toString()` 抛 TypeError（引擎捕获打警告，不崩溃）。复核可达性：确认框 `modal` 遮罩拦截鼠标、`uiLocked()` 拦截 Ctrl+W/doQuit/onClosing，所有关闭路径实际不可达；且 onAccepted 已有 `doc &&` 空值防御。建议改 `doc && doc.url ? ... : 0` 或打开时记录 url 字符串。不修复的影响：仅极端程序化路径下的 console 警告。
2. **[可选] 打开路径双遍解码** `src/storage/encodingdetector.cpp:26-28` + `src/storage/localstorage.cpp:24-28` — 无 BOM 文件打开时 detect 全量解码产出并丢弃一份 QString，LocalStorage 再解码一遍。复杂度仍 O(n)（满足"数 MB 无可感延迟"），仅大文件（数十 MB）时峰值内存多一份 UTF-16 拷贝（raw + 临时 + content ≈ 4× 文件大小）。不修复的影响：大文件打开内存峰值偏高、耗时多一遍解码，无可感功能影响。
3. **[可选] encode 缺代码页可用性探测** `src/platform/gbkcodec.cpp:178-216` — decode 失败路径有 `cp936Available()` 探测，encode 无；极端裁剪系统上整串调用失败后错误归因为"第 1 行的字符 X 无对应编码"而非"系统缺少 CP936"。保存被正确阻止、磁盘安全，仅提示语义不准。建议 encode 失败路径先查 `cp936Available()`。
4. **[可选] 行号断言偏弱** `tests/test_core/tst_documentmanager.cpp`（`saveWithEncodingUnencodableFailsAndReverts`）与 `tests/test_core/tst_localstorage.cpp`（`gbkUnencodableWriteFailsAndKeepsDisk`）— 行号断言用 `error.contains("2")` 子串匹配，错误消息同时含临时目录路径（QTemporaryDir 随机名理论上可含数字），存在假通过窗口。tst_gbkcodec 的 `encodeReportsFirstBadCharOnCorrectLine` 已用精确"第 3 行"断言；建议这两处同样匹配"第 2 行"。
5. **[pre-existing] saveAs 覆盖重载不钳制光标** `src/document/documentmanager.cpp:259-260` — `reloadWithEncoding` 对光标做了新内容长度钳制，saveAs 的 shadowed 重载路径（基线既有，本次仅加编码参数）未钳制。复核影响：shadowed 光标超界时由 EditorArea/TextArea 消化，会话恢复有 qBound 钳制，无实际损坏路径。建议后续统一。

**边界行为确认（非缺陷，实证记录）**：
- 含 U+FFFD（GBK 坏字节解码产物）的文档直接保存 GBK 会失败并提示（U+FFFD 无 CP936 映射）——符合"不可编码即失败"需求语义，防坏字节信息静默丢失；用户可转 UTF-8 保存。
- 含半角 ¥（U+00A5）的内容保存 GBK 失败（CP936 无直接映射，全角 ￥ U+FFE5 有映射）——`WC_NO_BEST_FIT_CHARS` 正确阻止了 best-fit 静默替换为 '?'（探针实证无标志时确实替换）。
- GBK 解码的逐单元回退分支为防御性路径（当前 Windows NLS 表下 CP936 结构合法对全指派，不可达），保留合理。
- CP936 将 GBK 未指派位映射到 PUA 区：含此类字节的文件解码为 PUA 字符（显示为豆腐块），GBK 往返字节保持——CP936 实现固有特性，DEC-009 范围内。
