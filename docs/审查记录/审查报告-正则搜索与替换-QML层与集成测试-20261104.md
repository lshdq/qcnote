### 重点核查项核验（任务指定）

**（a）MultiCursorLayer 行为零变化 —— 成立**
- 逐行比对基线内联实现与 HighlightSegments.js：parsePairs 与原 selectionPairs 逐字符一致；segmentsForRanges 的 emit/push/二分/toEdge/空段跳过/外层 '\n' 拆段全部原样提取，仅参数化（闭包变量→入参），语义等价。
- 依赖追踪等价：原绑定内 `_layoutDeps = [ed.wrapMode, ed.width, ed.contentHeight]` 与 `ed.text` 的读取，现于绑定求值期间同步调用的库函数内读取——QML 绑定对求值期间（含被调 JS 函数内）的 QObject 属性读取同样计入依赖，`.pragma library` 不影响该机制（HighlightSegments.js 文件头已注明此约束并要求调用方在 property 绑定内同步调用；两调用方均满足）。
- 测试证明：基线已存在的 test_editor tc008/tc008b（selectionSegments 对独立参考实现的逐段断言：计数/宽度/y 严格递增/toEdge 兜底/NoWrap 单段）重构后全绿，即零变化的回归证据。

**（b）EditorArea 防环链路与 activeEditor 生命周期 —— 成立**
- 新增 SearchController 编辑走 QTextDocument 直改：TextArea.onTextChanged→（text≠doc.content）selfContentSync 置位回写 doc.content→delegate onContentChanged 被 selfContentSync 短路；控制器自身 contentsChange 被 m_applyingEdits 短路——双向防环完整（tc101 断言 modified 为真，回写链实证）。
- 控制器 select 设原生选区→editor.onCursorPositionChanged→selfCursorSync 置位回写 doc.cursorPosition→doc 信号下行被短路——与既有光标同步防环同模式，无新环。
- activeEditor/activeMc 生命周期：onIsActiveChanged（激活上移/失活比对置空）+ Component.onDestruction（同对象比对置空）双路径；切标签时先 B 激活后 A 失活的乱序下，A 的置空有 `=== editor` 身份守卫不会误清 B。置 null → searchCtl.target/textDocument 绑定重估 → setTextDocument(null) 主动 disconnect 旧 QTextDocument（searchcontroller.cpp:42-44），无悬挂连接；文档对象销毁时 contentsChange 连接随 QObject 析构自动断开，无泄漏。
- 滚动监听 Connections 只读（scrollCursorIntoView 不改匹配/选区/文档状态），Qt.callLater 回调内再次校验 activeEditor 与 currentIndex，无循环、无悬挂闭包。

**（c）Main.qml uiLocked 完备性 / Shortcut 冲突 —— 成立**
- 入口枚举：全部 do*（含 cycleTab、searchJumpGlobal、onClosing）均有 uiLocked guard；TitleBar/Toolbar/DocumentTabs 无窗口级 Shortcut（grep 证实），模态期间鼠标被 overlay 阻断、键盘焦点被对话框 focus:true 夺取。
- F3 两态：Shortcut 处理器按 searchDialog.visible 分流——打开态转发 doFindNext/doFindPrev（焦点可能在选项/按钮上，转发必要且正确，与输入框 Enter 不重复执行：findField Keys 只处理 Return/Enter）；关闭态走 searchJumpGlobal（含 uiLocked/pattern/matchCount 守卫）。Ctrl+F/H 在对话框已开时经 openSearchDialog 的 uiLocked 分支改聚焦（查找框全选），其他模态打开时无操作。
- onClosing：searchDialog.visible 在 uiLocked 内 → 模态期间拒绝窗口关闭，与其他模态一致。

**（d）SearchDialog 状态管理 —— 成立**
- 复位矩阵：hasJumped 于 onAboutToShow / findField.onTextChanged / 三开关 onToggled / trackedDocument（textDocument 重绑，跨文档 F3 首跳不跳过首个匹配）复位；lastReplacedCount 于 onAboutToShow 与各查找/替换动作出口复位（doReplaceAll 写入新值）。trackedDocument 经 `property var` 绑定 + 共用 NOTIFY 的值比较，仅文档对象实际变化才触发。
- 跳转出口 jump(forward) 的首跳语义（hasJumped=false 且编辑器选区≠currentRange → select 定位而不推进）与"打开即选中的词上按 Enter 应跳到下一处"的编辑器惯例一致；选区已等于 currentRange 时按 findNext 推进，正确。
- 打开/重复打开：openFind/openReplace 先 open()（同步 aboutToShow 回填）再聚焦；已开时由 Main 分支聚焦不重置状态（会话延续，合理）。

**（e）SearchHighlightLayer 纯视觉边界 —— 成立**：无 MouseArea/无按键处理，anchors.fill 不消费事件；active=false 时整体隐藏且 matchSegments/currentSegments 绑定早退不计算；overflowed 时 EditorArea 传 [] 的约定落实（EditorArea.qml:263），当前匹配描边（1 段）保留符合 DEC-004「导航仍可用」。

**（f）AppTheme token 合规 —— 成立**：新增 searchMatch/searchMatchBorder 两 token（含语义注释与透明度选型依据）；SearchHighlightLayer/SearchDialog 引用 token；唯一非 token 色值 `"transparent"` 为结构性透明（仅描边不填充，非主题色，有注释），不属散落硬编码。非颜色线索：描边（形状）+ 状态文本 + enabled 置灰，均满足。

**（g）tests/test_searchui 质量 —— 合格**：真实事件驱动（QKeyEvent 直发窗口走 QQuickWindow 真实派发、QMouseEvent 真实点击驱动复选框 toggled、QMetaObject 调 QML 函数走真实代码路径，且注释明确说明了为何不用程序化 toggle）；断言全部针对业务结果（编辑器文本、计数/索引/选区区间、modified、可见性、按钮 enabled、状态行文本）；每用例独立 Bench + 清空残余文档 + 会话重定向 QTemporaryDir + QCNOTE_TEST_SHELL_NOOP 隔离；offscreen 双保险（main qputenv + CMake ENVIRONMENT），无可见窗口，符合项目 GUI 红线。

## 4. 其他发现（复核后成立，按严重度排序）

1. **[可选] 死状态：SearchDialog.focusMode** — 证据：src/qml/SearchDialog.qml:31,220-221,225-226（声明 + openFind/openReplace 赋值，全文件无读取）。根因：聚焦动作由 openFind/openReplace 直接调用对应 focus 函数完成，focusMode 未参与任何逻辑。影响：无功能影响，仅冗余状态，读者需额外确认其用途。建议：删除该属性或让 focus 逻辑消费它；不修复则维持 3 行冗余。

2. **[可选] 布局硬编码耦合：对话框顶部对齐 y=96** — 证据：src/qml/SearchDialog.qml:56-58（注释"标题栏 40 + 工具栏 44 + 间距 12"）。根因：Popup 不支持任意 anchors，y 取常量；TitleBar/Toolbar（Main.qml:398-419）高度将来调整时 96 不会跟随。触发条件/放大路径：仅当布局高度变化时对话框错位（遮挡工具栏或离编辑区过远），当前布局下正确（tc201 断言通过）。影响：低，可维护性问题。建议：改为对 titleBar/toolbar 实际高度求值的绑定（经根窗口引用传入），或至少在 TitleBar/Toolbar 高度定义处加注释声明 96 的依赖关系；不修复则未来调整布局时需记得同步。

3. **[可选] IME 组合态 Enter 拦截未列入人工验证清单** — 证据：src/qml/SearchDialog.qml:86-94,116-124（Keys.onPressed BeforeItem 优先级接受 Return/Enter）。根因：中文输入法组合（拼音未上屏）时按 Enter 确认候选，Windows 平台多数情况该键经 VK_PROCESSKEY 转输入法事件、不走普通 KeyPress 派发，但不同输入法行为有差异，BeforeItem 处理器在 TextField 之前执行，若组合态 Return 作为普通键派发则会被拦截执行跳转而非确认上屏。触发条件：特定输入法/平台组合（可达性未在本环境证实，故不定级更高）。影响：若成立，中文用户查找框输入体验受损（无法用 Enter 上屏）。建议：加入测试报告「人工待验」清单（组合态按 Enter 应上屏而非跳转）；如人工复现，改为检查 `event.count === 0 && !findField.inputMethodComposing` 类守卫或改用 onAccepted 处理。测试用例 TC-201 人工部分当前未含 IME 场景。

4. **[可选][pre-existing] closeDocumentWithConfirm 无 uiLocked 守卫** — 证据：src/qml/Main.qml:234-242（函数体无 guard），入口 TitleBar onRequestCloseTab（Main.qml:407）直达。当前不可达：模态 overlay 阻断标签关闭按钮的鼠标点击、键盘焦点在对话框内、Ctrl+W 走有 guard 的 doCloseActive。根因：既有代码的防御模式是「do* 函数 guard + 模态 overlay 物理阻断」双层，closeDocumentWithConfirm 是唯一从 UI 控件直达且缺第一层的路径（基线即如此，本次 uiLocked 新增 searchDialog 未改变其可达性）。影响：防御深度不对称，未来若 TitleBar 增加键盘入口或模态属性调整，可能出现查找对话框与未保存确认框同时打开。建议：顺手在函数开头加 uiLocked() guard 与其余 do* 对齐（一行，零行为变化——当前路径本就不可达）；不修复则依赖 overlay 阻断持续成立。

5. **[可选] 集成测试分支缺口** — 证据：tests/test_searchui/tst_searchuiintegration.cpp 覆盖 11 条主链路，未覆盖：① 对话框已开时再按 Ctrl+F/Ctrl+H 的聚焦分支（Main.qml:191-199）；②「关闭」按钮（RejectRole）点击路径（仅 Esc 已测，二者汇入同一 rejected，风险低）；③ F3 在对话框打开态的真实按键转发（Main.qml:481-498 的 Shortcut 分流，现以 invokeDialog("doFindNext") 等价覆盖）。影响：上述分支为真实入口但无回归断言，回归时只能靠人工发现。建议：后续补 3 个小用例（每约 10 行，均可复用现有 Bench 桩）；不补则维持现状风险（声明式一行的 Shortcut/分支，风险低）。
