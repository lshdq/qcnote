## 4. 深度核查记录（高风险路径专项）

以下疑点经逐层追踪后**排除**（列出以供后续审查复用）：

1. **模态关闭时 WM_ACTIVATE 重入 poll → 嵌套 showModal**：DialogHost 关闭时序（dialog.cpp:125-134）中 `DestroyWindow`/`SetActiveWindow` 触发的 owner 重激活 WM_ACTIVATE 到达时，要么 `wasActive` 已翻 true（`g_windowActive && !wasActive` 为 false），要么 `active_` 仍为 true（UiLocked 兜底，`active_ = false` 在 `SetActiveWindow` 之后执行）——两路径均不可达重入。系统文件对话框同理由 `g_fileDialogOpen` 成对置位覆盖（main.cpp:809-811/842-844）。
2. **findings 循环中 `doc` 悬垂**：模态期间宿主 EnableWindow(FALSE) + WM_CLOSE 被拒（C4）+ 转发队列推迟（UiLocked 重试路径）→ 无文档销毁路径；`Document::applyLoadedState` 等链内调用不销毁文档。
3. **打字期间快照吸收窗口**（DEC-010 修复目标）：`OnDocumentMetadataChanged` 仅 url 变化才刷新（main.cpp:576-581），`OnDocumentModifiedChanged` 仅脏→干净翻转刷新——打字（保持脏）不重置快照，已核实无吸收路径。
4. **stat 采样竞争窗口**（status 成功 ↔ last_write_time 之间文件被删）：timeEc/sizeEc → nullopt 本轮跳过 → 下轮 not_found 正常报 Deleted——降级方向安全。
5. **`poll({doc})` braced list 绑定**：签名为 `const std::vector<Document*>&`（头文件:110），合法。
6. **`baselineHash` 口径**：sha256Hex(m_baseline)，m_baseline 为内存统一形态（LF/无 BOM/UTF-8，document.cpp:138-141）与 `LocalStorage::read` 归一化内容同口径——内容比对无编码/换行假阴性。
7. **core 分层纪律**：externalchangemonitor.h/.cpp 仅 include 标准库 + `core/document.h`，无 Win32/UI 头；`Finding::doc` 为 const 指针——分层依赖方向合规。
8. **自测钩子无生产后门**：`windowForTest`/`dialogWindowForTest`/`EditorTextOf`/`TypeIntoEditor`/`ReadFileBytes` 均为既有函数（diff 中仅调用无定义），`--watch-interval-ms`/`--selftest-filewatch` 为启动参数非持久状态。
9. **脏文档「重新加载」失败后的恢复路径**（快照已推进、同 stat 不重弹）：存在三条用户可达恢复（文件 stat 再变自动重弹、「文件→按编码重新加载」既有菜单、关闭重开），非死锁——降级为可选建议（见其他发现 2）。

## 5. 其他发现（经复核成立，按严重度排序）

**无阻塞项、无应改项。** 以下为可选项：

1. **[可选] 防御性编程: `PollActiveDocumentNow` 入口未自检 UiLocked — 证据：src/main.cpp:1039-1041（入口直接 poll，守卫依赖 3 个调用点：main.cpp:521-523、4683、4997） — 根因：守卫约定靠调用方纪律维持，注释虽有声明（main.cpp:1037-1038）但无结构性保障 — 触发条件/放大路径：未来新增调用点（如新的立即触发钩子）漏检守卫时，在模态循环泵消息栈内重入 poll，可能对已处理 finding 的文档重复弹框 — 影响：当前版本不可达（3 个调用点均已核），风险仅在后续演进 — 建议：入口加一行 `if (UiLocked()) return;` 自守卫，把「模态期间跳过检测」从调用方约定固化为函数不变式；不修复的影响：依赖人工审查维持约定，漏检时表现为重复弹框（不损坏数据）。**
2. **[可选] 交互完整性: 脏文档三选框选「重新加载」失败后的错误框未告知恢复路径 — 证据：src/main.cpp:1086-1089（`ShowErrorDialog(L"重新加载失败", ...)` 仅 url+错误消息） — 根因：快照推进语义（DEC-008 自限设计）使同 stat 版本不再重入决策，但错误框文案没有提示用户如何重试 — 触发条件/放大路径：文件被第三方独占锁定等低频场景，用户选「重新加载」失败后若文件 stat 不再变化，三选框不再出现 — 影响：用户可能困惑重试入口（实际存在：文件再变自动重弹、「文件→按编码重新加载」、关闭重开），数据安全无影响（内存内容未丢失） — 建议：错误框消息追加一句恢复路径提示（如「文件可能正被其他程序占用，可稍后重试或经 文件→按编码重新加载 手动载入」）；不修复的影响：低频边界下用户需自行发现重试路径。**
3. **[可选] 前瞻兼容: stat 采样与内容判定的存储 scheme 分发不对称 — 证据：src/main.cpp:993（StatFileForWatch 直接 `std::filesystem::status`，无 storageForUrl 判定） vs src/main.cpp:1022（DiskContentMatchesBaseline 经 `g_docManager.storageForUrl(path)` 分发） — 根因：当前唯一 `file://` scheme 下两者等价，无实际缺陷 — 触发条件/放大路径：项目演进路线明示「本地文件 → 网络存储扩展」（.opencode/AGENTS.md 项目概述），届时非本地 scheme 的 stat 将被 filesystem::status 误判（网络 URL 路径按 not_found/错误处理），与内容判定的 storageForUrl 分发不一致 — 影响：纯前瞻性，当前版本零影响 — 建议：在 StatFileForWatch 注释中标注「非 file:// scheme 扩展时需与 storageForUrl 对齐分发」（当前 DEC-009 注释已钉住三分语义但未覆盖 scheme 维度）；不修复的影响：未来扩展时需重新发现此不对称。**
